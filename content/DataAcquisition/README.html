数据采集

数据采集以 C# 项目的形式编写：每个项目是一个文件夹，由 DataMaster 工作台编译、运行和热重载

Important

自 v3.27.0 起，旧版画布式「构建运行」工程不再受支持

项目结构

新建项目会生成以下标准框架（示例项目名 LineA，它同时是根命名空间）：

LineA/
├─ LineA.csproj                      # 仅供 Visual Studio / Rider 打开，平台编译不读取它
├─ appsettings.json                  # 设备、数据库连接参数（新建时是占位值，改好才能运行）
├─ AGENTS.md                         # 项目架构说明，写给 AI 助手和新同事
├─ GlobalUsings.cs                   # 各层的全局 using 与命名空间声明
├─ Startup.cs                        # 唯一的启动入口，也是项目的「任务清单」
├─ CollectTask/                      # 采集任务（与 PLC 程序块的文件夹对应）
│  ├─ DataReader/                    # PLC 上报的数据，一个结构体对应一个 DB（标准三件套）
│  │  ├─ ProductInfoStruct.cs        #   产品信息 DB10100
│  │  ├─ ProductRouteEventStruct.cs  #   产品流转事件 DB10101
│  │  └─ InteractionSignalEventStruct.cs # 交互信号事件 DB10102
│  ├─ DataWriter/SystemStruct.cs     # 上位机写入：系统区 DB10200（心跳、错误码、错误次数等）
│  └─ TaskExecution/
│     └─ CollectTaskExecution.cs     # 触发区 DB10000 / 完成区 DB10001 布局与各任务地址 CollectTaskArea
├─ ReplyTask/                        # 业务任务（示例 Inspect：DB11000/11001、请求 DB11100、应答 DB11200）
│  ├─ DataReader/InspectRequestStruct.cs
│  ├─ DataWriter/InspectReplyStruct.cs
│  ├─ TaskExecution/ReplyTaskExecution.cs
│  └─ Handlers/InspectTaskHandler.cs # 判定与决策逻辑
├─ StepTask/                         # 步序控制（示例 Station：状态 DB12100、命令 DB12200）
│  ├─ DataReader/StationStatusStruct.cs
│  ├─ DataWriter/StationCommandStruct.cs
│  └─ Sequences/                     # StationStep 步骤枚举、StationStepWorker 步序服务
├─ DataAccess/
│  ├─ Entities/                      # 实体：Product_Info、Product_Route_Event（外键指向产品信息）、Interaction_Signal_Event
│  ├─ Mappers/                       # 结构体 → 实体（事件时间解析失败时取当前时间并在备注中留痕）
│  └─ Repositories/                  # （可选）自定义仓储，添加采集任务时生成
├─ Models/                           # 其它数据模型（枚举、DTO 等）
├─ Workers/SystemWorker.cs           # 每秒写系统区；定时任务也放这里
└─ libs/                             # （可选）第三方 dll，放进来即可引用

新建项目自带标准采集任务（产品信息、产品流转事件、交互信号事件）与系统区，地址对应 PLC 程序块 DataMaster/CollectTask，基本每个案子都用得上，现场不上报的任务留着即可；Inspect（业务应答）、Station（步序控制）是示例，照着改名或删除。

启动入口

public sealed class Startup : IMasStartup {
    public void ConfigureServices(IServiceCollection services, MasContext context) {
        services.AddPlc("Line1");      // 设备，参数在 appsettings.json 的 Devices:Line1
        services.AddDatabase("Main");  // 数据库，参数在 Databases:Main；采集任务会为自己的实体建表
        services.AddHostedService<SystemWorker>();    // 系统区：心跳、错误码、错误次数

        // 标准采集任务：产品信息先于流转事件注册（后者的外键指向前者的表）；现场不上报的任务留着即可，不触发就不会执行
        services.AddCollectTask<ProductInfoStruct, ProductInfoEntity, ProductInfoMapper>("Line1", "Main", CollectTaskArea.ProductInfo);
        services.AddCollectTask<ProductRouteEventStruct, ProductRouteEventEntity, ProductRouteEventMapper>("Line1", "Main", CollectTaskArea.ProductRouteEvent);
        services.AddCollectTask<InteractionSignalEventStruct, InteractionSignalEventEntity, InteractionSignalEventMapper>("Line1", "Main", CollectTaskArea.InteractionSignalEvent);

        // 业务应答任务 Inspect：触发 → 读 InspectRequestStruct → InspectTaskHandler 处理 → 写 InspectReplyStruct
        services.AddReplyTask<InspectRequestStruct, InspectReplyStruct, InspectTaskHandler>("Line1", ReplyTaskArea.Inspect);

        // 步序控制 Station：等到位 → 动作并下发命令 → 等完成 → 复位
        services.AddHostedService<StationStepWorker>();

        // @mas-register：新任务的注册行插在此行之上（工作台「添加任务」与 Agent 使用，请保留）
    }
}
  • 所有服务都通过构造函数注入。按名称注册的服务（设备、数据库）使用 [FromKeyedServices("名称")] 指定
  • 后台服务按注册顺序启动，因此依赖数据库表的服务要注册在建表之后

任务模板

在工作台中选择「添加任务」（或 Agent 工具 dataAcquisition.scaffold），会按模板生成任务文件，并把注册行插入 Startup.cs 中 // @mas-register 标记之上，热重载后生效

  • 生成的文件名与类型名都带任务名前缀（Part → PartStruct、PartEntity、PartMapper、PartRepository）
  • 同类任务共用一个 XxxTaskExecution.cs：第一次添加时按填写的触发区、完成区地址创建，之后只在其中追加该任务的触发字段（ReadPart）和地址方法（CollectTaskArea.Part），填写的触发区、完成区地址不再使用。字段顺序就是 PLC 中的偏移，删任务时记得同步删字段，并与 PLC 数据块核对
  • 表名由任务名转成 snake_case 再补 _records（Part → part_records）
  • 地址默认取项目中已用最大地址之后的下一个整百，多个地址依次 +1，请与 PLC 程序核对
  • 找不到 // @mas-register 标记时不会自动注册，需要手动把注册行加进 ConfigureServices
  • 生成的文件开头都带一段说明头（GENERATED +「生成说明」+ 版权），标明来自哪个模板、可以直接修改
模板 生成的文件 注册
采集任务 CollectTask/DataReader/XxxStruct.cs、DataAccess/Entities/XxxEntity.cs、DataAccess/Mappers/XxxMapper.cs、DataAccess/Repositories/XxxRepository.cs；CollectTask/TaskExecution/CollectTaskExecution.cs 追加 ReadXxx 与 CollectTaskArea.Xxx AddCollectTask<XxxStruct, XxxEntity, XxxMapper, XxxRepository>(设备, 数据库, CollectTaskArea.Xxx)
业务应答任务 ReplyTask/DataReader/XxxRequestStruct.cs、ReplyTask/DataWriter/XxxReplyStruct.cs、ReplyTask/Handlers/XxxTaskHandler.cs；ReplyTask/TaskExecution/ReplyTaskExecution.cs 追加 RequestXxx 与 ReplyTaskArea.Xxx AddReplyTask<XxxRequestStruct, XxxReplyStruct, XxxTaskHandler>(设备, ReplyTaskArea.Xxx)
单向任务 ReplyTask/DataReader/XxxRequestStruct.cs、ReplyTask/Handlers/XxxTaskHandler.cs；与业务应答任务共用 ReplyTaskExecution.cs AddTriggerTask<XxxRequestStruct, XxxTaskHandler>(设备, ReplyTaskArea.Xxx)
步序控制 StepTask/DataReader/XxxStatusStruct.cs、StepTask/DataWriter/XxxCommandStruct.cs、StepTask/Sequences/XxxStep.cs、XxxStepWorker.cs AddHostedService<XxxStepWorker>()
定时任务 Workers/XxxWorker.cs AddHostedService<XxxWorker>()
  • 任务模板随平台发布，位于 MAS.Runtime 的 Templates/DataAcquisition/Items/<标识>/：文件夹里的每个文件首行 //#path: 相对路径 指定生成位置，第二行为 //#once 的是同类任务共用的文件（只在不存在时创建）
  • item.json 描述标题、说明、所需参数（设备、数据库）、要填写的地址、注册行，以及 inserts（插入共用文件中 // @mas-field、// @mas-area 等标记之上的行）。新增一种任务模板只需在这里加一个文件夹（构建时嵌入程序集，不落输出目录，因此删除或改名不会在 bin 里留下旧副本）

系统区

Workers/SystemWorker.cs 每秒把 SystemStruct 整块写入 PLC（地址 SystemWorker.ADDRESS），PLC 据此判断上位机是否在线、有没有出错：

字段 类型 内容
Heartbeat INT 每秒加 1，0 ~ 32767 循环
ErrorCode INT 0 正常；2 处理失败（如写库失败）；3 超时；4 忙；≥100 业务码。出错的任务恢复后自动清零
RunMode String[10] appsettings.json 的 System:RunMode
Payload String[100] 最近一次错误的摘要，如 PartStruct#123 code=2
Timestamp String[22] 上位机时间 yyyy-MM-dd HH:mm:ss.ff
Version String[10] System:Version
PcId String[20] System:PcId，默认计算机名
ErrorCount DINT 自启动以来的错误次数，每次失败都计一次（包括写库失败后的重试）
SuccessCount DINT 自启动以来的处理成功次数，采集任务即保存成功的条数
  • 错误码和计数来自运行时自动注册的 IAcquisitionStatus：采集、应答、单向任务每次处理后自动上报；应答任务的业务码（≥100）是处理器给出的正常结论，不计为错误。用户代码也可以注入它，调用 ReportError / ReportSuccess 上报自己的错误
  • S7 的 String[n] 在 PLC 里占 n + 2 字节（含最大长度、实际长度两个头字节），字段要标 [S7String(S7StringType.S7String, n)]，只能写 ASCII；MC/Modbus 没有字符串头，改用 [FixedString(n)]
  • 字段可以按现场 PLC 的数据块增删，SystemStruct 与 PLC 的布局保持一致即可

采集任务

采集任务在一个任务内完成整个采集链路，保存成功后才回写完成值，PLC 看到完成值即可确认数据已保存。采集任务只用触发区、完成区和数据区，没有应答区：

PLC 写数据 → 触发值 +1 → 读 XxxStruct → XxxMapper.Map → XxxRepository.AddAsync → 插入一行 → 回写完成值

// CollectTask/TaskExecution/CollectTaskExecution.cs（添加任务时自动追加）
public struct CollectTaskExecution { public short ReadPart; }

public static class CollectTaskArea {
    public const int EXECUTION_ADDRESS = 100;
    public const int COMPLETED_ADDRESS = 101;

    public static void Part(HandshakeOptions o) => Configure(o, nameof(CollectTaskExecution.ReadPart), dataAddress: 102);
}

// CollectTask/DataReader/PartStruct.cs
[StructLayout(LayoutKind.Sequential, Pack = 1)]
public struct PartStruct { public int SerialNo; public float Value; public short IsOk; }

[DbHandler(true)]
[Table("part_records", DisplayName = "Part")]
public class PartEntity {
    [Column("Id", "INT", IsPrimaryKey = true, IsAutoIncrement = true, IsNullable = false)]
    public int Id { get; set; }
    // ……
}

public sealed class PartMapper : IDataMapper<PartStruct, PartEntity> {
    public PartEntity Map(PartStruct source) {
        if (source.SerialNo <= 0) {
            throw new ReplyRejectedException(101, "序号无效"); // 丢弃：不入库，照常回写完成值
        }

        return new PartEntity { SerialNo = source.SerialNo, Value = source.Value, CreatedAt = DateTime.Now };
    }

    public PartStruct MapBack(PartEntity? destination) => default;
}
  • 写库失败、影响行数为 0 或超时：不回写完成值，按 RetryInterval 重试同一触发值，直到保存成功
  • 映射器抛出 ReplyRejectedException：数据不入库，记录警告，照常回写完成值（表示有意丢弃这条数据）
  • 全部采集任务共用一个触发 DB 和一个完成 DB，布局由 CollectTaskExecution 的字段顺序决定，偏移用 Marshal.OffsetOf 算出，例如三个任务的触发值都在 DB10000、完成值都在 DB10001，偏移分别为 0、2、4：
[StructLayout(LayoutKind.Sequential, Pack = 1)]
public struct CollectTaskExecution {
    public short ReadProductInfo;            // 偏移 0
    public short ReadProductRouteEvent;      // 偏移 2
    public short ReadInteractionSignalEvent; // 偏移 4
}

public static class CollectTaskArea {
    public const int EXECUTION_ADDRESS = 10000; // CollectTaskExecution
    public const int COMPLETED_ADDRESS = 10001; // CollectTaskCompleted

    public static void ProductRouteEvent(HandshakeOptions o) => Configure(o, nameof(CollectTaskExecution.ReadProductRouteEvent), dataAddress: 10101);
}
  • MC/Modbus 的偏移按寄存器计，要把 Configure 里的偏移改为 offset / 2
  • 启动时自动为实体建表并补充缺失的列，因此采集任务的实体不必再在 AddDatabase 里登记一次
  • 入库默认使用基类仓储；需要去重、修改已有记录或写多张表时，在 DataAccess/Repositories/XxxRepository.cs 中重写 AddAsync（注册的就是该仓储），业务代码用 db.Repository<XxxEntity, XxxRepository>() 取得同一个仓储
  • 采集任务流程固定；需要把处理结果告诉 PLC，或超出「一行一表」的需求（跨表事务、查重后更新）建议改用业务应答任务，在处理器里注入 IDatabase 自行处理

设备

设备直接写在 appsettings.json 的 Devices:<名称> 下，也可以在工作台的「设备」面板中添加、修改、删除并测试连接（只写入所选协议用到的参数，改名后需同步 Startup.cs 里按字符串引用的名称）：

{
  "Devices": {
    "Line1": { "Protocol": "S7", "Ip": "192.168.0.1", "CpuType": "S7-1500", "Rack": 0, "Slot": 1 },
    "Press": { "Protocol": "MC", "Ip": "192.168.10.2", "Port": 3000, "Frame": "MC3E" },
    "Robot": { "Protocol": "ModbusTcp", "Ip": "192.168.10.3", "Port": 502, "UnitId": 1 }
  }
}
协议 地址含义
S7 address 是 DB 号，offset 是字节偏移
MC / ModbusTcp address 是起始寄存器，offset 直接叠加到地址上
  • Protocol 必须显式填写，缺省时启动会报错。
  • 首次读写时自动连接。读写失败时会断开连接并抛出异常，下一次读写时自动重连。
  • 同一台设备的读写按顺序执行。
  • 项目运行期间，设备以设备名登记到平台。视觉模块的「通讯设备」和 Agent 的 PLC 技能通过该名称使用同一条连接。
public sealed class StationStepWorker([FromKeyedServices("Line1")] IPlc plc) : BackgroundService {
    protected override async Task ExecuteAsync(CancellationToken stoppingToken) {
        while (!stoppingToken.IsCancellationRequested) {
            // 等 PLC 到位：300 是状态区地址（S7 为 DB 号，MC/Modbus 为起始寄存器）
            await plc.WaitUntilAsync<StationStatusStruct>(300, s => s.Ready == 1, token: stoppingToken);

            // 上位机动作完成后允许 PLC 动作：301 是命令区地址
            await plc.WriteAsync(new StationCommandStruct { Start = 1, Step = 2, Result = 1 }, 301, token: stoppingToken);
        }
    }
}

握手任务

下位机写好请求后，将触发值加 1。上位机处理完成后，将完成值写成与触发值相同的值。触发值和完成值均为 16 位整数（INT）。

注册方式 流程
AddTriggerTask<TRequest, THandler> 触发 → 读请求 → 处理 → 回写完成值
AddReplyTask<TRequest, TReply, THandler> 触发 → 读请求 → 处理 → 写应答 → 回写完成值 
public struct InspectRequestStruct { public short RecipeNo; public float Value; }
public struct InspectReplyStruct { public short ResultCode; public short RequestIndex; public short IsOk; }

public sealed class InspectTaskHandler(ILogger<InspectTaskHandler> logger) : IReplyHandler<InspectRequestStruct, InspectReplyStruct> {
    public Task<InspectReplyStruct> HandleAsync(HandshakeContext<InspectRequestStruct> context, CancellationToken token) {
        if (context.Request.RecipeNo <= 0) {
            throw new ReplyRejectedException(101, "配方编号无效");
        }

        return Task.FromResult(new InspectReplyStruct { IsOk = (short)(context.Request.Value >= 85 ? 1 : 0) });
    }
}
  • 应答任务应答先于完成值写入。下位机看到完成值变化后，即可读取应答
  • 启动时读取一次完成区。完成值等于触发值，表示该请求已处理，重启后不会重复执行
  • 触发值为 0 表示复位，之后再出现的 1 按新请求处理
  • 同一个任务内，处理器不会被并发调用。处理器实现 IDisposable 或 IAsyncDisposable 时，在停止时释放
  • 可配置的选项：PollInterval（轮询间隔，默认 50 ms）、HandlerTimeout（处理超时，默认 5 s）和 RetryInterval（通讯失败后的重试间隔，默认 1 s）

应答约定字段

应答结构体中，以下整数字段按名称匹配：

字段 必填 说明
ResultCode 是 结果码，由框架填写；缺少该字段时启动失败
RequestIndex 否 框架回填本次的触发值
结果码 含义
1 成功（处理器返回的结果码为 0 时，框架改为 1）
2 处理器抛出异常；或 ReplyRejectedException 给出的结果码 ≤ 1
3 处理超时
4 上一次处理超时后仍未结束，本次没有交给处理器
≥ 100 业务自定义，由处理器自己填写，或通过 ReplyRejectedException 指定

失败应答中，除约定字段外，业务字段均为默认值。下位机应先判断结果码，再使用业务字段。

情况 应答任务 单向任务 采集任务
处理器异常 / 超时 写失败应答，照常回写完成值 记录错误，照常回写完成值 不回写完成值，按重试间隔重试
ReplyRejectedException 应答其结果码，照常回写完成值 记录错误，照常回写完成值 丢弃本条，照常回写完成值
上一次仍未结束 应答「忙」，照常回写完成值 不回写完成值，等上一次结束后再处理本次 同单向任务
读取请求或写入失败 不回写完成值，按重试间隔重试 同左 同左

数据库

{
  "Databases": {
    "Main": {
      "Server": "127.0.0.1",
      "Port": 3306,
      "Database": "linea",
      "User": "root",
      "Password": "enc:……"
    }
  }

  • 数据采集项目只支持 MySQL。启动时自动建库、建表、补列、补索引
  • 在工作台的「数据库」面板中添加、修改并测试连接。密码加密后才写入 appsettings.json（以 enc: 开头），也可以让 Agent 用 dataAcquisition.database 工具保存。加密方式与平台自身的数据库密码相同，因此项目文件夹复制到另一台安装了 DataMaster 的电脑后仍可使用
  • 手工写入配置的明文密码会在打开项目时自动加密。运行时遇到明文密码，也会在输出中给出警告
  • 运行监视面板显示每个数据库的状态、写入次数和最近一次错误
[Table("Part_Records")]
[DbHandler(true)]
public class PartEntity {
    [Column("Id", "INT", IsPrimaryKey = true, IsAutoIncrement = true, IsNullable = false)]
    public int Id { get; set; }

    [Column("SerialNo", "INT", IsNullable = false)]
    public int SerialNo { get; set; }
}

public sealed class SaveHandler([FromKeyedServices("Main")] IDatabase db) : ITriggerHandler<UploadRequest> {
    public async Task HandleAsync(HandshakeContext<UploadRequest> context, CancellationToken token) {
        // db.Repository<PartEntity>()                  用默认仓储
        // db.Repository<PartEntity, PartRepository>()  用自定义仓储（重写了入库逻辑时用这个）
        await db.Repository<PartEntity, PartRepository>().AddAsync(new PartEntity { SerialNo = context.Request.SerialNo });
    }
}
  • 向 AddDatabase 传入实体类型时，启动时也会建表；采集任务会自动为自己的实体建表。依赖这些表的服务必须注册在建表之后
  • 需要执行 SQL 或事务时，使用 db.Operations
  • 列名不要使用 MySQL 保留字

常见问题

现象 处理
提示「缺少设备配置 Devices:xxx」 AddPlc 的名称必须与 appsettings.json 中的键一致
提示「必须有且只有一个 IMasStartup 实现」 检查 Startup.cs 是否被删除，或是否存在多个启动类
新建项目一运行就连不上 设备的 IP、数据库参数还是占位值，先改 appsettings.json（或在工作台里改设备、数据库）
后台服务显示「异常退出」 在运行监视中查看原因，或在输出面板中查看完整异常。其他服务不受影响
停止后提示「项目程序集未能完全卸载」 项目代码中存在静态事件、未退出的线程或计时器。热重载仍可使用，但内存会逐次增长。请在停止时释放这些资源
