更新源搭建与发布

更新源就是一个支持 HTTP GET 的静态文件服务：自建的 nginx / IIS 站点、阿里云 OSS、腾讯云 COS 甚至内网共享的 HTTP 服务都可以。客户端只做两件事：读取 manifest.json，下载清单里指定的更新包。

从自建站点迁到对象存储时，只需要把主程序设置页里的更新源地址换掉，其余不用改动。

目录结构

更新源上的结构固定为「根地址 / 通道 / 文件」：

<更新源根地址>/
├─ stable/                                             正式通道
│   ├─ manifest.json
│   ├─ MasDataMaster-win-x64-v3.22.0.7z
│   ├─ MasDataMaster-win-x86-v3.22.0.7z
│   ├─ MasDataMaster-win-x64-self-contained-v3.22.0.7z
│   └─ MasDataMaster-win-x86-self-contained-v3.22.0.7z
└─ beta/                                               预发布通道
    ├─ manifest.json
    └─ MasDataMaster-win-x64-v3.23.0-beta.7z

客户端请求的清单地址是 {更新源根地址}/{通道}/manifest.json。 清单里的包地址支持相对路径（相对清单所在目录）与绝对地址，因此包体可以和清单放在一起， 也可以单独放到 CDN 上。

方案一：自建服务器

nginx

server {
    listen 443 ssl;
    server_name update.example.com;

    ssl_certificate     /etc/nginx/ssl/update.crt;
    ssl_certificate_key /etc/nginx/ssl/update.key;

    root /var/www/update/mas-datamaster;

    # 清单必须每次取到最新的，否则发布后客户端会继续读到旧版本
    location ~ /manifest\.json$ {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
        expires -1;
    }

    # 更新包内容不可变，可以长缓存
    location ~ \.(7z|zip)$ {
        types { }
        default_type application/octet-stream;
        expires 30d;
    }
}

创建目录并放开权限：

sudo mkdir -p /var/www/update/mas-datamaster/{stable,beta}
sudo chown -R $USER:$USER /var/www/update/mas-datamaster

IIS

IIS 默认不识别 .7z，未添加 MIME 类型时下载会返回 404：

# 添加 .7z 的 MIME 类型
Add-WebConfigurationProperty -PSPath 'MACHINE/WEBROOT/APPHOST' -Filter "system.webServer/staticContent" `
    -Name "." -Value @{fileExtension='.7z'; mimeType='application/octet-stream'}

另外把站点的请求大小限制放开（requestLimits maxAllowedContentLength），并给 manifest.json 配置 Cache-Control: no-cache。

验证

curl -I https://update.example.com/stable/manifest.json
curl -I https://update.example.com/stable/MasDataMaster-win-x64-v3.22.0.7z

两个请求都应返回 200，包体的 Content-Length 要与清单里的 size 一致。

方案二：对象存储（OSS / COS）

以阿里云 OSS 为例，腾讯云 COS 步骤相同（术语换成"存储桶"与"访问权限"）：

  1. 创建 Bucket：地域选离现场最近的；读写权限选公共读（私有读需要签名 URL， 当前客户端不支持带签名的下载）。
  2. 建立目录：在 Bucket 里创建 stable/ 与 beta/。
  3. 上传文件：包体与 manifest.json 上传到对应通道目录。
  4. 设置 manifest.json 的缓存头：在对象的 HTTP 头里把 Cache-Control 设为 no-cache。 这一步很关键 —— 默认缓存会让现场在发布后几小时内仍读到旧清单。
  5. 绑定自定义域名并开启 HTTPS（可选但建议）：证书配好后更新源地址就是 https://update.example.com/mas-datamaster。
  6. 开启 CDN 加速（可选）：包体可长缓存；发布新版本后必须刷新 manifest.json 的 CDN 缓存。

命令行上传（ossutil）：

ossutil cp MasDataMaster-win-x64-v3.22.0.7z oss://mas-cloud/stable/
ossutil cp manifest.json oss://mas-cloud/stable/ --meta=Cache-Control:no-cache

对应的更新源地址填 https://mas-cloud.oss-cn-shanghai.aliyuncs.com； 若把包放在 Bucket 的子目录下（如 mas-datamaster/stable/），更新源地址就是 https://mas-cloud.oss-cn-shanghai.aliyuncs.com/mas-datamaster。

设置页只填根地址，通道不用填：客户端固定读 stable，「加入内测」开启时再读一次 beta 并取版本高的一方。所以 stable/ 必须始终存在，beta/ 可以没有

发布：CI 自动推送

.github/workflows/release.yml 在推送 v* 标签时构建 4 个包 （win-x64 / win-x86 × 框架依赖 / 自包含），产物为 7z。

推送目标是阿里云 OSS（update-channel 任务用 ossutil 上传），需要在仓库设置里配置：

类型 名称 说明
变量 UPDATE_PUBLISH_ENABLED 设为 true 才会执行推送任务
变量 UPDATE_OSS_BUCKET Bucket 名，如 mas-cloud
变量 UPDATE_OSS_ENDPOINT 地域接入点，缺省 oss-cn-shanghai.aliyuncs.com
变量 UPDATE_OSS_PREFIX Bucket 内子目录，留空则 stable/、beta/ 直接建在 Bucket 根下
变量 OSSUTIL_VERSION ossutil 版本，缺省 1.7.19，一般不用填
机密 UPDATE_OSS_ACCESS_KEY_ID RAM 用户的 AccessKey ID
机密 UPDATE_OSS_ACCESS_KEY_SECRET RAM 用户的 AccessKey Secret

通道由标签自动判定：带 - 的预发布标签（如 v3.23.0-beta）进 beta，其余进 stable。 推送顺序是先传包体再传清单，避免现场读到指向尚未上传包体的清单；包体上传时带 Cache-Control: max-age=2592000，清单带 Cache-Control: no-cache，不需要事后手工改元数据。

上传完成后 CI 会匿名回读一次 manifest.json 并与本地产物比对，Bucket 权限不是公共读时当场失败。

给 CI 用的 RAM 用户按最小权限授权即可，自定义策略示例（把 mas-cloud 换成实际 Bucket）：

{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["oss:PutObject", "oss:GetObject"],
      "Resource": ["acs:oss:*:*:mas-cloud/stable/*", "acs:oss:*:*:mas-cloud/beta/*"]
    }
  ]
}

发布：手工上传

没有配置 CI 推送，或者需要临时发一个版本时：

# 1. 发布并打包（四种组合按需执行）
pwsh scripts/Update/New-UpdatePackage.ps1 -Version v3.22.0 -Rid win-x64
pwsh scripts/Update/New-UpdatePackage.ps1 -Version v3.22.0 -Rid win-x86
pwsh scripts/Update/New-UpdatePackage.ps1 -Version v3.22.0 -Rid win-x64 -SelfContained
pwsh scripts/Update/New-UpdatePackage.ps1 -Version v3.22.0 -Rid win-x86 -SelfContained

# 2. 汇总生成清单
pwsh scripts/Update/New-UpdateManifest.ps1 `
    -PackageDirectory build/update-dist `
    -Tag v3.22.0 `
    -PolicyPath scripts/Update/update-policy.json `
    -OutputPath build/update-dist/manifest.json

产物在 build/update-dist/：*.7z、*.package.json（哈希与体积元数据）与 manifest.json。 把 *.7z 与 manifest.json 上传到 <更新源>/stable/ 即可，先传包体再传清单。

打包脚本会依次从 PATH、7-Zip 安装目录、NuGet 缓存里寻找 7-Zip 命令行； 本机没有 7-Zip 时可以加 -Format zip（更新器两种格式都支持，只是包体更大）。

上线前检查

发布正式通道之前，建议按顺序验证：

  1. 本地联调：用 Start-UpdateServer.ps1 起一个本地更新源，走通"检查 → 下载 → 退出 → 更新 → 重启"；
  2. beta 通道试点：先在一两个现场把通道切到 beta 验证；
  3. 确认版本闸门：本次是否有破坏性变更，需要抬高 scripts/Update/update-policy.json 的 minimumVersion；
  4. 确认包体可下载：curl -I 检查清单与包体都是 200，size 与实际一致；
  5. 确认清单不被缓存：改动清单后立即 curl 一次，看是否拿到新内容；
  6. 推正式通道。

本地联调：

# 版本号要高于当前运行的版本，否则不会提示更新
pwsh scripts/Update/New-UpdatePackage.ps1 -Version v9.99.0

# 按通道整理：build/update-dist/stable/{manifest.json, *.7z}
pwsh scripts/Update/Start-UpdateServer.ps1 -Root build/update-dist -Port 8099

# 主程序设置页：更新源 http://127.0.0.1:8099，通道 stable

现场部署注意

  • 应用目录必须可写。装在 C:\Program Files 下时普通用户没有写权限，更新会失败并回滚； 建议装到 D:\MasDataMaster 这类目录，或以管理员身份运行。
  • 应用目录所在磁盘要有 2 倍应用体积的空余：解压出的新内容与备份会同时存在于暂存目录中。
  • 杀毒软件可能锁住刚写入的文件。更新器对每个移动操作重试 12 次（约 5 秒），仍失败则回滚； 建议把应用目录加入白名单。
  • 首次上线仍然需要人工部署一次，在线更新只负责后续版本。

版本回退

在线更新只升不降：清单版本低于现场版本时不会提示更新，因此把清单换回旧版本不会让已升级的现场降级。 需要降级时只能人工部署旧版本包。

发现新版本有问题时的正确做法是：把清单换回旧版本（阻止尚未更新的现场继续升级）， 再对已升级的现场人工回退。
