会话工件与参数引用

会话工件用于将大规模结构化数据保存在磁盘中，避免数据直接进入模型输出和会话上下文，从而降低 Token 消耗并减少长会话中的上下文膨胀

适用场景

在典型的组态生成流程中，通常需要经过以下步骤：

读取图纸/Excel → 解析 IO → 创建结构体 → 创建画面并绑定

当 IO 数量达到数百或数千条时，如果直接通过会话传递数据：

  1. 解析结果需要进入上下文
  2. 后续工具调用又需要将相同数据重新组织为参数
  3. 大规模工具参数还会保留在会话历史中，并持续占用后续上下文

会话工件通过文件引用代替大规模参数传递，使数据可以在工具之间直接流转，而模型仅保留必要的引用和摘要信息。

Runtime 的工具目录负责控制工具 Schema 的上下文占用；会话工件进一步控制实际数据产生的上下文开销。

存储位置

工件按会话隔离存储：

<GlobalDefaultPath.BasePath>/PrismaAgent/artifacts/<sessionId>/
├── io-points.json          脚本产物
└── io-ops.json             脚本生成的批量操作

模型仅通过当前会话中的工件名称访问文件。

不同会话之间无法读取或写入彼此的工件。以下工件名均不允许使用：

  • ..
  • 绝对路径
  • Windows 盘符路径
  • 任何一级分量是目录联接或符号链接的路径

非法路径会直接拒绝，不进行自动修正。

前三类路径风险可通过字符串规范化直接拦截；junction 与符号链接则不能仅依赖字符串校验。

即使路径字符串本身合法，会话目录内的 junction 或符号链接仍可能将实际访问目标指向目录之外。由于工件读取属于低风险、免审批操作，解析路径时会逐级检查各级分量，一旦发现重解析点立即拒绝访问。

会话工件目录本身不存在使用链接的合理场景，因此采用“发现重解析点即拒绝”的策略。相比解析真实路径后再校验边界，这种方式更易审计，也能减少路径解析过程中的竞态窗口。

会话目录根路径不执行该检查，因为该路径由宿主负责推导，其上级用户目录本身可能处于系统重定向或链接环境中。

工件默认保留，不自动清理，便于后续排查和复查。

工件来源

来源 说明
script.python 默认工作目录为当前会话工件目录，脚本生成的文件可直接作为工件使用
ARTIFACTS.md 模型自己维护的工件索引，说明每个工件是什么、依赖什么、是否还需要

出参不自动搬运

工件机制仅作用于入参。工具结果原样进入上下文，执行管线不负责截断、落盘或改写。

工具结果的规模控制由工具自身负责。目前各类本地工具均已提供对应的限制或分页机制：

工具 自带限制或分页能力
cli.read_file offset / maxChars / totalChars / truncated
cli.grep maxMatches
cli.diff maxLines
cli.run、script.* stdout / stderr 由进程运行器限制长度
dynamicViews.query / model.get offset / limit

执行管线不再额外包装工具结果，避免同时存在两套语义不同的游标。源工具游标通常指向源文件或源数据，而外层游标只能指向当前结果正文；两者混用容易导致错误读取且难以发现。

因此，结果规模控制遵循以下原则：

结果规模的边界由产出结果的工具负责，而不是由执行管线统一兜底。

如果新工具可能返回大量数据，应在工具协议中直接提供 offset、limit、maxChars 等限制或分页能力，而不是依赖执行管线进行二次搬运。

参数引用

支持工件引用的工具参数可以使用：

{
  "ops": {
    "$artifact": "io-ops.json",
    "offset": 0,
    "limit": 500
  }
}

其中：

  • offset：顶层 JSON 数组的起始位置
  • limit：本次读取的最大元素数量

offset / limit 是可选的。批量写入工具没有条数上限，整批一次提交才是原子的——拆成多段反而会在中途失败时留下半成品工程。分段用于失败后续传或有意分阶段上线，不是常规批量的做法。

单次展开有一道体量闸：正文超过 16 MB 直接判错并提示分段。展开要经过「读成字符串 → 解析成对象树 → 重新序列化 → 跨 IPC」，峰值内存是文件本身的若干倍，而 IPC 帧上限是 128 MB。这道闸放在展开器而不是某个工具里，因为它保护的是所有开放了工件引用的参数。

可通过二者对大型工件进行分批处理。

工件引用仅在工具调用派发时展开。展开后的实际数据不会写回会话历史，因此上下文中始终只保留工件引用。

参数授权

工具必须显式声明允许使用工件引用的参数：

var schema = ToolSchema.Object()
    .ObjectArray("ops", BuildModelOpSchema, "Ordered operations.", isRequired: true)
    .AllowArtifact("ops");

return new ToolDefinition {
    ParametersJsonSchema = schema.Build(),
    ArtifactParameters = schema.ArtifactParameters,
    // ...
};

AllowArtifact 同时负责：

  • 将参数 Schema 扩展为“原始参数或工件引用”
  • 将参数加入 ToolDefinition.ArtifactParameters 授权列表

只有经过授权的参数才能使用 $artifact。

未授权参数包含 $artifact 时，调用会直接拒绝，不会派发给工具。

检测到 $artifact 即按工件引用处理。 若 $artifact、offset 或 limit 的格式无效，则直接返回工件引用格式错误，不再按普通参数继续处理，以避免无效引用绕过校验

授权信息会随 tool.list 跨 IPC 传递，因此宿主进程注册的工具同样可以支持工件引用。

工件工具

工具 用途
artifact.list 查看当前会话的工件及其大小、元素数量和写入时间
artifact.read 分页读取工件；JSON 数组使用 offset / limit，其它内容使用 charOffset

artifact.read 主要用于结构检查、抽样和错误排查。结果会返回 hasMore 及下一页游标（nextOffset 或 nextCharOffset），可据此连续读取。

需要注意：

  • artifact.read 不在散装工具之列，其结果不会被二次截断——它本来就是一次定量的分页读取
  • 读取过程采用流式处理，仅保留当前切片所需数据，避免因大型工件产生不必要的内存占用
  • 目录里存在 ARTIFACTS.md 时，artifact.list 会把它顶到结果最前面，提示模型先读索引

当完整数据需要传递给其他工具时，应优先使用工件引用，而不是重新加载到会话上下文。

不提供写入与删除能力

artifact.write 与 artifact.delete 均不提供，这是有意设计。

  • 写入：工件内容通常应由 script.python 直接生成，或通过 cli.write_file 写入。由模型直接调用写入工具会额外消耗输出 Token，也容易形成不必要的数据搬运
  • 删除：工件用于保留会话执行记录，不应作为低风险、免审批操作提供。删除需求由 cli 处理，并遵循对应的高风险审批流程

artifact.* 与 cli.* 在文件读写能力上存在一定重叠，但寻址范围不同：

  • $artifact 仅支持引用会话工件目录中的文件
  • cli 写入其他目录的文件不能通过 $artifact 引用
  • artifact.read 还提供低风险免审批、数组元素切片读取，以及结果不参与二次截断等能力

推荐流程

script.python
  解析图纸 / Excel
  → io-points.json

script.python
  根据 io-points.json 生成操作
  → io-ops.json

model.apply
  validateOnly
  + ops={"$artifact":"io-ops.json"}

model.apply
  校验通过后去掉 validateOnly 整批提交

在该流程中，大规模 IO 数据可以直接在脚本、工件和工具之间流转，无需逐条进入模型上下文。

对于批量写入类工具，建议同时提供：

  • 干跑校验能力；
  • 失败记录原文回显。

模型可以先完成完整校验，再针对失败记录修正数据生成逻辑，避免在大量操作中逐条排查
