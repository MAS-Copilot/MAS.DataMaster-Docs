会话历史架构

架构目标

  • 完整聊天历史持久化
  • 模型推理上下文恢复
  • 多会话独立运行
  • 会话切换与历史重放
  • 临时对话
  • 后台会话持续执行
  • 中断后的安全恢复

系统将以下三类状态明确分离：

层级 职责
展示历史 保存用户可见的完整会话过程
推理上下文 保存模型继续对话所需的上下文
会话运行时 保存当前进程内的执行状态

三者生命周期不同，不相互替代

展示历史

展示历史采用事件日志模型

IConversationJournal 是会话展示事件的统一入口，负责：

  • 接收会话事件
  • 实时派发给界面
  • 持久化事件
  • 保证事件顺序

历史记录保存的是用户实际看到的过程，而不是模型上下文

典型事件包括：

user.message
assistant.text
tool.call
tool.done
system.notice
turn.started
turn.ended
turn.truncated

完整取值见 ConversationEventTypes。其中 system.notice 用于本轮压根没有发给模型的情形，由系统给出的提示占掉模型回复的位置

事件在单个会话内保持严格顺序

历史重放

IConversationReplayService 负责根据事件日志重建会话界面

核心原则：

实时事件 ──┐
           ├──> applyConversationEvent ──> UI
历史事件 ──┘

实时显示和历史恢复使用同一套事件处理逻辑。

历史重放只恢复展示状态，不重新执行：

  • 模型请求
  • 工具调用
  • 审批
  • 计划
  • 其他具有副作用的操作

因此：

Event Log 是展示状态的事实来源

推理上下文

展示历史不能替代模型推理上下文

模型上下文由 AgentSession 维护，并通过 IAgentCheckpointService 进行持久化和恢复

Checkpoint 保存继续对话所需要的模型状态，例如：

  • Conversation Items
  • 已激活工具状态
  • 已执行工具调用标识
  • Usage
  • 上下文压缩状态

Checkpoint 与展示事件日志相互独立：

Conversation Events
    ↓
恢复用户看到的内容

Agent Checkpoint
    ↓
恢复模型继续思考所需状态

Checkpoint 无法恢复时，只影响继续原对话，不影响历史查看

会话运行时

长期运行中的会话由 IConversationManager 统一管理。

每个会话对应独立 ConversationRuntime，Runtime 保存当前进程内的执行状态，例如：

  • 当前轮次
  • CancellationToken
  • 执行任务
  • 会话状态
  • 未读状态

基本规则：

  • 同一会话同时只执行一个轮次
  • 不同会话可以并发运行
  • 切换会话不会停止原会话
  • 停止操作只影响目标会话

因此会话生命周期不与当前 UI 页面绑定

轮级状态隔离

具有轮次状态的组件不能跨轮次长期共享。

逻辑结构：

ConversationRuntime
       │
       ├── Turn 1
       │    └── AgentLoop
       │
       ├── Turn 2
       │    └── AgentLoop
       │
       └── Turn N
            └── AgentLoop

每轮执行拥有独立的：

  • Agent Loop
  • Tool Pipeline
  • Channel State
  • Tool Mapping
  • Approval State

避免并发会话之间发生状态污染

待回答交互

审批、计划等需要等待用户响应的交互属于 Pending Interaction 它们不是长期历史的一部分，而是运行时交互状态。由：

ConversationInteractionPresenter
IPendingInteractionStore

负责管理。

每个 Pending Interaction 必须绑定：

Conversation
    └── Turn
         └── Interaction

后台会话产生交互时不能直接覆盖当前会话界面。用户重新进入对应会话后，再恢复其未完成交互

会话切换

会话切换分为：

激活目标会话
      ↓
重放目标历史
      ↓
恢复运行时状态
      ↓
恢复 Pending Interaction
      ↓
继续接收实时事件

切换只改变当前正在查看的会话。

后台会话：

  • 可以继续生成
  • 可以继续执行工具
  • 可以继续记录事件
  • 不向当前页面派发展示事件

重新切回后，通过历史重放补齐期间产生的内容

激活会话

当前界面只允许显示一个激活会话。由 IActiveConversationTracker 维护当前激活状态。

事件流：

Conversation Event
       │
       ▼
Event Dispatcher
       │
       ├── Active Conversation
       │       ↓
       │      UI
       │
       └── Background Conversation
               ↓
            只持久化

从而实现后台生成与前台展示解耦

临时对话

临时对话是会话级属性

Conversation
├── Persistent
└── Temporary

临时会话：

  • 正常进入运行时
  • 正常调用模型
  • 正常执行工具
  • 正常显示事件

但不进入持久化历史。临时状态必须在会话正式产生内容前确定

编辑与截断

编辑最后一条消息属于会话历史分叉。模型上下文和展示历史分别处理：

Agent Context
    ↓
移除旧轮次上下文

Event Log
    ↓
追加 turn.truncated

历史事件仍保持 Append Only。Replay 根据截断事件计算最终展示状态。这样既保留事件完整性，又允许修改最后一轮对话。

会话元数据

会话列表使用独立的 Conversation Metadata。主要包含：

Conversation
├── Id
├── Title
├── CreatedAt
├── LastActiveAt
├── Status
└── HasUnread

Conversation Metadata 与 Conversation Events 分离：

Conversation
    │
    ├── Metadata
    │
    ├── Events
    │
    └── Checkpoint

侧栏负责展示和切换会话，而不是承载运行时状态本身

元数据分工写入

Title、Status、HasUnread 均由专用语句更新，事件日志的 upsert 只维护活动信息：

字段 写入者 时机
LastSequence / LastActiveAt 事件日志 用户消息、轮次收尾
Title / TitleStatus 标题服务 首条用户消息落库后异步生成
Status 会话管理者 开始写 Running，收尾写 Idle / Failed
HasUnread 会话管理者 后台轮次收尾置位，用户进入后清除

日志中的标题和状态只是占位值，整体覆盖会把真实标题抹成 NULL，或将 Running 错写为 Idle。

除事件活动外，其他元数据更新都不推进 LastActiveAt，避免侧栏排序无故变化。

读取 Status 时，如果数据库仍为 Running，但进程内已无对应运行时，说明上一进程中途退出，应显示为「已中断」。无需启动时回写，直到该会话再次运行。

序号游标先与数据库对齐

事件表 (ConversationId, Sequence) 唯一，写入使用 INSERT IGNORE 以支持队列安全重试。因此，分配新序号前必须先对齐数据库最大序号，否则冲突事件会被静默丢弃。

典型场景是首次打开历史会话：内存游标仍为 0，若直接续写，新事件会从 1 开始，与历史数据冲突

ConversationJournal 因此在首次分配序号时惰性对齐：

  • 仅仓储成功返回最大序号后标记已对齐
  • 若待写队列已有序号，则整体重排到最新游标之后

会话标题

会话标题属于会话元数据。由独立的 IConversationTitleService 负责生成和更新。

标题生成与主 Agent Loop 解耦：

User Message
     │
     ├── Main Agent
     │
     └── Title Service

标题生成失败不影响主对话

持久化模型

持久化层包含以下四类逻辑实体：

Conversation
│
├── Conversation Events
├── Agent Checkpoint
└── Attachments
实体 职责
Conversation 保存会话元数据
Conversation Events 保存用户可见的完整会话历史
Agent Checkpoint 保存模型继续会话所需的上下文
Attachments 保存附件引用与元数据，文件内容存储于磁盘

各实体职责独立，不交叉承担持久化责任。

附件

用户消息由有序内容分段组成，包括文本、图片和文件。分段顺序即模型接收顺序，持久化和映射过程中不得重排。

核心约束：

  • 仅保存引用，不保存 Base64。事件、检查点和附件记录仅保存 attachmentId / fileName / mediaType / byteSize / relativePath，文件内容仅在构造模型请求时读取并编码
  • 仅保存相对路径。避免全局存储目录变更后导致历史附件路径失效
  • 附件存储于全局数据目录，不得写入可能被应用更新覆盖的安装目录
  • 附件不按文本估算 Token。图片按视觉 Token 估算，文件按字节数估算；上下文压缩仅保留附件说明，不读取正文
  • 导入阶段执行体积校验：单文件 < 50 MB，同一会话累计附件总量 ≤ 50 MB。当前使用 store: false，每轮请求都会重新发送完整上下文，因此累计上限作用于整个会话

承载方式

附件根据扩展名划分为三种承载方式。分类结果不单独持久化，历史附件在需要发送时按照相同规则重新判定。

类型 覆盖范围 模型输入
图片 .png .jpg .jpeg .gif .webp input_image
文档 .pdf 及 Office 文档格式 input_file
文本 通用文本、数据文件、标记文件、源码与配置文件 读取正文并以内联 input_text 发送

源码和配置文件通常不适合作为 input_file 交由服务端文档解析器处理，因此优先在本地读取正文并以内联文本发送。

内联文本会包含原始文件名。内容超过允许长度时进行截断，并在文本中明确标记截断状态，避免模型将不完整内容误认为完整文件。

当文件无法按 UTF-8 或 UTF-16 正常解码时，不以内联文本发送，而是回退为 input_file。

不支持的附件

无法映射到上述三种承载方式的附件，例如压缩包、可执行文件、音频和视频文件，不发送给模型。

处理规则如下：

  • 用户消息仍正常写入会话事件流，并追加一条 system.notice 事件作为提示
  • 当前轮次不进入 Agent 编排，该消息不会加入模型上下文
  • 提示内容在事件创建时确定并持久化；重新打开会话时直接重放该事件，不重新生成提示

核心架构原则

  • 展示与推理解耦：Event Log != Agent Context，一个负责“用户看到了什么”，一个负责“模型接下来需要知道什么”

  • UI 与运行时解耦：Conversation Runtime != Current Page，切换页面不会终止后台会话

  • 实时与重放统一

    Realtime Event
Replay Event
      ↓
Same Reducer
    • 避免维护两套界面逻辑

  • 会话之间完全隔离

    Conversation A Runtime
Conversation B Runtime
Conversation C Runtime
    • 运行任务、取消、工具状态、Pending Interaction 均不得相互污染

  • 历史事件只追加：Append Only Event Log，修改历史通过追加状态事件表达，而不是直接修改已有事件

  • 展示历史优先保证完整：即使模型上下文无法恢复，也应该能够完整查看已有聊天历史
